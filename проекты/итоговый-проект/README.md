## 1. Что нужно сделать

Представьте, что вы отвечаете за аналитику в компании ПРАЙМ. Руководитель хочет каждое утро получать небольшую сводку: сколько компания заработала, что происходит с подписками, растёт ли отток и почему изменились основные показатели.

При этом хотелось бы узнавать о проблемах заранее. Например, если резко выросло число отмен или перестали приходить данные о платежах, система должна это заметить и сообщить.

В рамках проекта вам предстоит разработать такую систему мониторинга. Она должна автоматически:

1. Получать данные из учебной базы ПРАЙМ и хотя бы одного внешнего источника.
2. Проверять качество загруженных данных.
3. Рассчитывать бизнес-метрики и объяснять изменения выручки с помощью факторного анализа.
4. Проверять показатели на аномалии и формировать уведомления.
5. Отправлять отчёты и уведомления в Telegram, обновлять дашборд.
6. Сохранять информацию о запусках и возникающих ошибках.

Большую часть необходимых инструментов мы уже разбирали на занятиях. В первом модуле вы рассчитывали метрики подписки, занимались факторным анализом, проверяли данные и учились избегать двойного счёта при соединении таблиц. Во втором модуле добавим работу с API, организацию Python-проекта, расписание, логирование, алёрты и дашборды.

Итоговый проект — возможность собрать всё это в одну систему, которая работает без необходимости каждый раз открывать ноутбук и запускать ячейки вручную.

## 2. Как работать с датами

Здесь есть особенность, которую важно учитывать с самого начала.

Наша учебная база содержит данные с 6 января 2025 года по 30 августа 2026 года. Новые записи в ней не появляются. Поэтому мы будем имитировать ежедневную работу системы на исторических данных.

У системы должно быть понятие даты отчёта. Например, если мы запускаем отчёт за 24 августа 2026 года, он должен анализировать события 23 августа и неделю, которая закончилась 23 августа.

Важное условие: при расчёте за определённую дату система не должна пользоваться информацией, которая стала известна позже. Если подписку отменили 25 августа, то в отчёте за 24 августа она ещё считается действующей.

Предусмотрите три способа запуска:

```bash
# Полный отчёт за конкретную дату
uv run prime report --date 2026-08-24

# Обработка следующего дня из истории
uv run prime replay

# Пересчёт периода без отправки в Telegram
uv run prime backfill --start 2026-03-01 --end 2026-03-31
```

Названия команд можно изменить, но эти три сценария должны поддерживаться.

Для `replay` начальная дата задаётся в конфигурации. После каждого успешного запуска система запоминает, какой день обработала, и при следующем запуске переходит к следующему.

Таким образом, можно поставить запуск раз в сутки и имитировать реальную работу. А можно запускать его раз в минуту и за несколько минут показать работу системы за неделю. Чаще одного раза в минуту запускать не нужно.

Отдельно определитесь, в каком часовом поясе рассчитываете дневные показатели: UTC или местное время клиента. Мы обсуждали эту проблему в теме 05. Выбранный вариант и его обоснование должны быть в README.

## 3. Требования к проекту

В обязательной части девять компонентов. Ниже перечислено, что должно работать в каждом из них и на каких занятиях мы это разбираем.

### 3.1. Структура проекта и запуск

Проект нужно оформить как Python-пакет с кодом в `src/prime/`.

Разделите код по назначению: получение данных, проверки, расчёт метрик, поиск аномалий, отправка результатов. Не обязательно делать сложную архитектуру, но структура должна быть понятной.

Ноутбуки можно использовать для исследования данных и проверки гипотез. Сам мониторинг должен запускаться без них.

Что обязательно:

- Параметры подключения к базе, схема, пороги алёртов, начальная дата и Telegram-чат задаются через конфигурацию.
- Пароли и токены хранятся в `.env`, а не в исходном коде.
- Вместо `print` используется логирование в файл. По журналу должно быть понятно, когда и за какую дату запускалась система, сколько данных получила, какие проверки прошли и что было отправлено.
- Секретные данные не должны попадать в логи.
- Проект должен запускаться на другом компьютере по инструкции из README: клонирование репозитория, `uv sync`, настройка `.env` и команда запуска.

Где разбираем: тема 09 и семинар С9, на котором будем переводить ноутбук первого проекта в Python-пакет.

### 3.2. Загрузка данных из учебной базы

Система должна самостоятельно получать данные из базы ПРАЙМ за необходимый период.

Не выгружайте таблицы целиком при каждом запуске. Например, если для отчёта достаточно дневного количества сессий, лучше посчитать его в SQL, чем загружать несколько миллионов строк в Python.

База общая для всех студентов. Если каждая команда будет ежеминутно считывать из неё миллионы строк, сервер не выдержит.

Требования:

- Загружайте только данные, необходимые для расчёта.
- Используйте параметризованные SQL-запросы, а не подстановку значений через f-строки.
- Сохраняйте загруженные данные локально: можно использовать SQLite, DuckDB или Parquet в `data/`.
- Повторная обработка одного и того же дня не должна создавать дубликаты.
- Локальное хранилище с данными добавьте в `.gitignore`.

Где разбираем: тема 10, семинар С10, ДЗ-4.

### 3.3. Внешние данные

Помимо учебной базы, подключите хотя бы один внешний источник с открытым HTTP API. Например, можно использовать:

- Курсы валют и ключевую ставку [Банка России](https://www.cbr.ru/).
- Рыночные данные через [MOEX ISS](https://iss.moex.com/).
- Публикуемые файлы [СберИндекса](https://sberindex.ru/ru/dashboards) — как дополнительный источник.

Внешние данные нужны не просто для выполнения требования. Подумайте, какую пользу они дают руководителю ПРАЙМ. Например, помогают понять, связаны ли изменения показателей компании с рыночной ситуацией. В README объясните, почему выбрали именно этот источник и как используете его в анализе.

Обязательные требования:

- HTTP-запросы выполняются с тайм-аутом и повторной попыткой при ошибке.
- Ошибки обращения к API записываются в журнал.
- Если внешний источник недоступен, основной отчёт всё равно формируется. В нём нужно указать, что внешние данные получить не удалось.
- Внешние показатели должны соответствовать дате исторического отчёта, а не текущему дню.

Готовые адреса запросов к Банку России и Мосбирже и их особенности — в приложении.

Где разбираем: тема 10, семинар С10, ДЗ-4.

### 3.4. Проверки качества данных

Перед расчётом метрик нужно убедиться, что исходные данные корректны.

Реализуйте не менее пяти проверок качества данных. Примеры проверок, которые имеет смысл сделать для ПРАЙМ, — в приложении.

Для каждой проверки укажите в README, что именно она контролирует, какие пороги используете и что происходит при ошибке. Например, система может пропустить расчёт недостоверной метрики, пометить её как проблемную или отправить отдельное предупреждение о качестве данных.

Где разбираем: С3 и `checks.py`, С4, тема 11 и семинар С11.

### 3.5. Расчёт метрик

Нужна витрина с не менее чем пятью бизнес-метриками, рассчитанными за день и за неделю.

Вы можете выбрать показатели, которые считаете наиболее полезными для мониторинга ПРАЙМ; список возможных — в приложении. Не нужно реализовывать всё сразу. Лучше выбрать пять-семь показателей, правильно их рассчитать и понимать, что они означают.

Для каждой метрики в README должны быть определение, зерно расчёта и объяснение, зачем она нужна бизнесу.

#### Факторный анализ

Кроме самих показателей, нужно объяснять изменение выручки.

Сравните последние семь дней с предыдущими семью и разложите изменение хотя бы по одной модели из темы 06. Например:

`Выручка = Активные подписки × Платежей на подписку × Средний платёж`

Можно использовать цепные подстановки, как на семинаре С6, либо анализ изменения по каналам привлечения, как на лекции.

Результат представьте в виде каскадной диаграммы. Её можно добавить в Telegram-отчёт или на дашборд.

Где разбираем: темы 05–06, семинары С5–С6, Проект 1.

### 3.6. Поиск аномалий и алёрты

Реализуйте не менее трёх правил, по которым система определяет, что произошло что-то необычное.

Какие именно события отслеживать, решаете вы. Но есть несколько важных условий.

Во-первых, проблемы с данными и изменения бизнес-показателей нужно различать. Если платежи за день не загрузились, нельзя сообщать руководителю, что выручка упала до нуля. В такой ситуации нужна ошибка качества данных.

Во-вторых, пороги должны быть обоснованы. Простое правило «выручка упала на 8 % относительно вчера» не всегда работает: у бизнеса могут быть различия между буднями и выходными, сезонность или обычные колебания. Можно сравнивать показатель с медианой за несколько предыдущих недель и учитывать разброс значений. При необходимости — отдельно для каждого дня недели.

В-третьих, система не должна отправлять одно и то же предупреждение каждый день. Если произошёл резкий рост отмен подписок, не нужно всю следующую неделю дублировать сообщение об одном и том же событии.

Обычные дни не должны сопровождаться тревогами.

Для каждого правила опишите в README, что оно отслеживает, как выбирается порог и почему вы считаете его подходящим. Подсказки, как устроить порог и не повторять тревоги, — в приложении.

Где разбираем: тема 11, семинар С11.

### 3.7. Telegram-бот и отчёты

Создайте Telegram-бота через [@BotFather](https://t.me/BotFather).

Каждый день система должна отправлять небольшую сводку с главными показателями и их изменениями. Можно добавить одну-две диаграммы.

Отчёт должен нормально читаться с телефона. Не нужно отправлять все рассчитанные таблицы целиком.

Предупреждения об аномалиях приходят отдельными сообщениями. Из сообщения должно быть понятно, какой показатель изменился, насколько сильно и что стоит проверить.

Для отправки достаточно двух методов Telegram Bot API: `sendMessage` и `sendPhoto`. Использовать отдельную библиотеку для бота необязательно.

Токен бота хранится в `.env`.

Также предусмотрите альтернативный способ получить отчёт: например, вывести его в консоль или сохранить в файл с помощью отдельного параметра запуска. Это понадобится, если на защите возникнут проблемы с интернетом.

Где разбираем: тема 11, семинар С11.

### 3.8. Дашборд

Сделайте простой дашборд, на котором можно посмотреть результаты мониторинга. Можно использовать Streamlit или Google Sheets.

На дашборде должны быть:

- Динамика основных метрик за выбранный период.
- Результаты проверок качества данных.
- История обнаруженных аномалий.
- Каскадная диаграмма факторного анализа.

Дашборд должен использовать уже рассчитанные и сохранённые данные. Не нужно каждый раз заново обращаться к учебной базе при переключении фильтров.

Где разбираем: тема 11, семинар С11.

### 3.9. Запуск по расписанию

Последняя часть — автоматизация.

Настройте запуск команды `replay` по расписанию на своём компьютере. Подойдут cron или launchd на macOS и Linux, Планировщик заданий в Windows.

Проверьте два сценария:

1. Система завершилась с ошибкой посреди обработки дня. При следующем запуске она должна корректно обработать этот день повторно, без частично записанных результатов.
2. Компьютер был выключен, и один или несколько запусков не состоялись. После включения система должна продолжить с первого необработанного дня, а не пропускать даты.

Для обязательной части достаточно расписания на вашем компьютере. Систему, которая круглосуточно работает на сервере, оцениваем отдельно — это дополнительное задание из раздела 9.

Где разбираем: тема 09, семинар С9.

## 4. Как будем проверять работу системы

В учебной истории есть несколько событий, по которым можно проверить, действительно ли мониторинг работает: дни без данных, неполная выгрузка, подорожание тарифов и массовые отмены подписок. Пять проверочных дат с описанием того, что случилось и чего мы ждём от системы, — в приложении. Прогоните систему на них до сдачи.

На защите мы будем запускать вашу систему на разных датах и смотреть, как она реагирует. В общих чертах ждём следующего:

- данных за день нет или они неполные — предупреждение о данных, а не вывод о падении выручки;
- в бизнесе произошло событие — предупреждение, из которого понятно, что изменилось и с чем это связано;
- одно событие — одно предупреждение, а не сообщение каждое утро;
- обычный день — обычный отчёт без предупреждений.

Важно: на защите даты будем выбирать мы. Помимо перечисленных событий, будем проверять и обычные дни.

Не нужно писать отдельные условия под конкретные даты из задания. Нам важно увидеть, что ваши правила действительно обнаруживают проблемы, а не просто узнают заранее известные события.

## 5. Как организовать работу

Проект достаточно большой, поэтому рекомендую не откладывать интеграцию до последней недели. Примерный план:

- **До 22 ноября.** Соберите команду в боте (`/team`), создайте репозиторий и распределите задачи. Начните переносить в Python-пакет то, что сделали в первом модуле: расчёт метрик, факторный анализ и проверки данных.
- **21–28 ноября.** На темах 09 и 10 разберём структуру пакета, конфигурацию, логирование, CLI и загрузку данных. К концу этого этапа желательно получить работающий `report --date` хотя бы для одной даты. Загрузка из базы и внешнего API входит в ДЗ-4.
- **5–12 декабря.** Добавьте проверки, алёрты, Telegram-бота, дашборд и расписание.
- **9 и 12 декабря.** На второй паре семинара пройдёт предзащита. У каждой команды будет пять минут, чтобы показать текущий результат и получить обратную связь. Оценку за предзащиту не ставим.
- **13–19 декабря.** Проверьте запуск проекта с чистого клона, прогоните систему на проверочных датах из приложения, закончите документацию и декларацию использования ИИ.
- **19 декабря.** Сдача проекта.
- **26 декабря.** Защита.

Постарайтесь как можно раньше получить минимальную работающую версию системы целиком. Когда отдельные компоненты впервые соединяются между собой, почти всегда обнаруживаются ошибки, которые не были видны при самостоятельном тестировании.

## 6. Как распределить задачи в команде

Каждый участник должен отвечать за определённую часть проекта, но при этом понимать, как она взаимодействует с остальной системой.

Например, в команде из трёх человек можно разделить работу так:

- **Участник 1 — данные.** Загрузка из учебной базы, подключение внешнего источника, проверки качества.
- **Участник 2 — аналитика.** Расчёт метрик, факторный анализ, поиск аномалий и правила уведомлений.
- **Участник 3 — инфраструктура и представление результатов.** Telegram-бот, дашборд, расписание, логирование, README.

Это пример, а не обязательное распределение. В команде из двух человек задачи можно объединить иначе.

Работайте через ветки и pull requests в общем репозитории. История коммитов должна позволять понять, кто над чем работал.

На защите вопросы будут как по вашей собственной части, так и по тому, как она связана с другими компонентами.

## 7. Что и куда сдавать

Один проект — один репозиторий на команду.

Создайте его из [шаблона проекта](https://github.com/tikhomirovd/prime-monitor-template), как мы делали с `prime-monitor`. Добавьте всех участников команды и пользователя `tikhomirovd` в Settings → Collaborators.

В репозитории должны быть:

- Исходный код: пакет `src/prime/`, `pyproject.toml`, `uv.lock` и `.env.example` без паролей и токенов.
- `README.md`: инструкция по установке, запуску и настройке расписания; описание выбранных метрик, проверок и алёртов; объяснение работы с историческими датами; известные ограничения системы.
- `КОМАНДА.md`: ФИО участников, логины GitHub и распределение ответственности. На основании этого файла будем задавать индивидуальные вопросы.
- `ДЕКЛАРАЦИЯ-ИИ-ЭКЗАМЕН.md`: заполненная декларация по шаблону. Каждый участник заполняет свою часть.
- Если претендуете на 9–10 баллов — раздел README о сервере: как развернуть систему на чистом сервере и как обновить её до новой версии (раздел 9).

Каждый участник команды должен самостоятельно отправить ссылку на общий репозиторий через команду `/submit` в [боте курса](https://t.me/hse_python_2627_bot).

Мы проверяем содержимое ветки `main` на момент последней отправки. Если после сдачи вы внесли изменения, отправьте ссылку ещё раз. Иначе новые коммиты не будут учтены.

## 8. Как проходит защита

Дата: 26 декабря. Продолжительность: 15 минут на команду.

**Первые 7 минут — демонстрация.** Мы называем дату, вы запускаете систему, и она формирует отчёт за нужный период. Показываете сообщения в Telegram, найденные аномалии, дашборд и журнал автоматических запусков. Затем запускаете обработку того же дня повторно, чтобы продемонстрировать отсутствие дубликатов.

**Следующие 8 минут — вопросы участникам.** Будем спрашивать про принятые решения и материал дисциплины. Например, почему вы выбрали конкретный порог алёрта, как работает проверка качества, откуда берётся число в отчёте или что произойдёт, если убрать одну из проверок.

Оценки за экзамен индивидуальные. Даже если система работает правильно, участник, который не может объяснить свою часть, получит более низкую оценку.

Также нужно ориентироваться в общей архитектуре проекта. Не обязательно помнить каждую строчку кода коллеги, но понимать, откуда приходят данные и как формируются итоговые результаты, необходимо.

## 9. Критерии оценки

Обязательная часть оценивается максимум в 20 первичных баллов.

1. **Полнота и работоспособность — 6 баллов (30 %).** Все девять компонентов реализованы и работают. Проект запускается с чистого клона по README. На проверочных датах система корректно формирует отчёты и предупреждения.
2. **Корректность метрик и проверок данных — 5 баллов (25 %).** Расчёты соответствуют эталонным значениям. Нет двойного счёта, выручка сходится с источником, проверки обнаруживают проблемы, а пороги алёртов обоснованы.
3. **Инженерное качество — 4 балла (20 %).** Структура проекта, конфигурация, хранение секретов, логирование, повторный запуск без дубликатов и корректная обработка ошибок.
4. **Индивидуальные ответы — 5 баллов (25 %).** Понимание собственной реализации, принятых решений и соответствующих тем курса.

Результат обязательной части переводится в экзаменационную оценку с коэффициентом 0,4. Таким образом, за обязательную часть можно получить максимум 8 баллов из 10.

### Дополнительное задание: система на сервере (+2 балла)

Ещё 2 балла можно получить за систему, которая развёрнута на сервере и работает без вас. Дополнительные баллы учитываются, если обязательная часть оценена не менее чем в 15 из 20 первичных баллов.

**+1 балл — развёртывание.** Разверните проект на VPS или на другой машине, которая работает круглосуточно: подойдёт и домашний компьютер, который не выключается, но не ноутбук, на котором вы работаете. Как организовать запуск — cron, systemd, Docker Compose или иначе, — решаете сами.

- Система запускается и работает на сервере без участия вашего компьютера.
- Зависимости и конфигурация на сервере настроены.
- Пароли и токены лежат в `.env` на самом сервере. Их нет в Git, в Docker-образе и в коде.
- В README описано, как развернуть систему на чистом сервере и как обновить её до новой версии.

**+1 балл — автономная работа.** Засчитывается только вместе с первым баллом. Недостаточно один раз запустить приложение на сервере — нужно показать, что оно работает само.

- `replay` запускается по расписанию и обрабатывает очередные даты.
- После перезагрузки сервера расписание работает без ручных действий.
- Ошибки записываются в журнал, и о неудачном запуске вы узнаёте сами — например, сообщением в Telegram.
- После сбоя система продолжает с первого необработанного дня.
- На защите есть журнал автоматических запусков минимум за последние 7 дней. Значит, сервер должен работать не позже чем с 19 декабря.

Круглосуточная работа не означает, что Python-процесс работает непрерывно. Сервер доступен всё время, а задача по расписанию запускается, отрабатывает и завершается.

На защите покажите конфигурацию развёртывания (без секретов), расписание, журнал запусков и отчёты, которые система сформировала сама.

**Пароль от учебной базы на сервере.** Для этого задания действует исключение из общего правила курса об учётных данных: пароль можно положить в `.env` на своём сервере, с доступом только у владельца файла (`chmod 600`). Нельзя класть его в репозиторий, Docker-образ и журнал, а также в секреты GitHub Actions и других сервисов, где его хранит не вы: такой вариант — только по согласованию с преподавателем. Ваша роль в базе и так только читает данные, отдельная роль для сервера не нужна.

Пошаговый минимум и типичные ошибки — в приложении.

## 10. Дедлайны и штрафы

По программе дисциплины работу необходимо сдать не позднее чем за три календарных дня до защиты. Поэтому действуют следующие сроки:

- **До 19 декабря, 23:59** — сдача без штрафа.
- **С 20 по 23 декабря, 23:59** — за каждые начатые сутки просрочки оценка за экзамен снижается на 1 балл. При этом штраф не снижает оценку ниже 4: если работа изначально оценена менее чем на 4, эта оценка сохраняется.
- **После 23 декабря, 23:59** — проект к защите не допускается, за экзамен выставляется 0 баллов.

### Что означает блокирующий экзамен

Если за экзамен вы получили меньше 4 баллов, итоговая оценка по дисциплине будет неудовлетворительной независимо от накопленной оценки.

При неудовлетворительном результате проект можно доработать с учётом замечаний и защитить повторно в сроки, предусмотренные графиком пересдач НИУ ВШЭ. Первую пересдачу принимает преподаватель, вторую — комиссия. Накопленная оценка при пересдаче не меняется.

## 11. На что обратить внимание перед сдачей

По опыту подобных проектов, больше всего проблем возникает не с расчётом отдельных метрик, а с тем, как вся система работает вместе.

Перед сдачей обязательно проверьте следующие ситуации:

- Проект разворачивается и запускается на другом компьютере по README, а не только на ноутбуке разработчика.
- Пароли и токены не попали в код, логи или историю коммитов.
- Отсутствующие дни действительно обнаруживаются, даже если в результатах группировки их просто нет.
- Неполная выгрузка не воспринимается как резкое падение бизнес-показателей.
- Одна аномалия не приводит к десяткам повторных уведомлений.
- Повторный запуск не создаёт дубликатов данных или сообщений.
- Правила мониторинга работают для произвольных дат, а не только для известных примеров.
- Есть возможность продемонстрировать результат без Telegram, если на защите возникнут проблемы с сетью.

Основная задача проекта — показать, что вы умеете не только проводить анализ в Python, но и организовать его в виде небольшой, надёжно работающей системы.

При этом не требуется строить промышленную платформу с десятками сервисов. Нам важнее корректные расчёты, понятная реализация и способность объяснить, почему вы сделали именно так.
