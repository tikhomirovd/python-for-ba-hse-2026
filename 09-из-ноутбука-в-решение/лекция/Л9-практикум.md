# Лекция 9. Практикум: из ноутбука в `prime report`

Сегодня вместо слайдов — практикум. Мы возьмём разведочный ноутбук и за шесть шагов превратим его в маленькую
систему: расчёт живёт в модуле, запускается одной командой, берёт настройки из `.env`, пишет журнал,
проигрывает историю по дням и не ломается от сбоя посреди дня. Ровно этот каркас нужен итоговому проекту:
в конце страницы — что из него куда идёт.

Как работаем. Главные строки каждого шага я пишу на экране, остальное берём готовым из репозитория
и разбираем. Вы повторяете у себя: печатаете вместе со мной или переключаетесь на готовый шаг командой
`git checkout -f step-N` (номер шага стоит в заголовке). Не успели, что-то не запустилось — не чините
на паре, догоните следующим шагом. Смотреть, не повторяя, — тоже нормальный способ пройти пару.

Данные — небольшой снимок ПРАЙМ прямо в репозитории. Ни сеть, ни учебный сервер сегодня не нужны.

|---|---|---|

он посчитает то же самое. Для исследования ноутбук хорош. Для того, что работает каждый день без вас, — нет.

## Шаг 1. Расчёт — в модуль · `step-1`

Первое, что делаем: вынимаем расчёт из ячеек в обычный файл Python внутри пакета `src/prime/`.
Функцию можно импортировать откуда угодно, у неё нет скрытого состояния, и она считает одинаково
при каждом вызове.

Расчёт делим на два файла по смыслу: `data.py` знает, откуда берутся данные, `metrics.py` — что из них
считается. Сейчас данные лежат в CSV, в итоговом проекте они придут из учебной базы. Когда источник
поменяется, править придётся только `data.py`.

`src/prime/metrics.py`:

```python
from datetime import date

import pandas as pd


def revenue(payments: pd.DataFrame, start: date, end: date) -> float:
    """Выручка по успешным платежам с start по end включительно."""
    paid = payments[payments["status"] == "success"]
    day = paid["paid_at"].dt.date
    in_period = (day >= start) & (day <= end)
    return float(paid.loc[in_period, "amount"].sum())


def new_subscriptions(subscriptions: pd.DataFrame, day: date) -> int:
    """Сколько подписок оформлено в этот день."""
    return int((subscriptions["started_at"].dt.date == day).sum())
```

Сверху вниз: оставляем успешные платежи, берём у каждого дату без времени, отмечаем те, что попали в период,
и складываем их суммы. Период задан двумя датами, а не строкой: так один и тот же код считает и день, и неделю.

`src/prime/data.py`:

```python
DATA_DIR = Path(__file__).resolve().parents[2] / "data"


def load_payments(data_dir: Path = DATA_DIR) -> pd.DataFrame:
    return pd.read_csv(data_dir / "payments.csv", parse_dates=["paid_at"])
```

`Path(__file__)` — это путь к самому `data.py`. Два шага вверх — корень проекта. Так файл находит данные,
откуда бы его ни запустили.

Ноутбук остаётся, но теперь он только вызывает функции:

```python
from prime.data import load_payments
from prime.metrics import revenue

payments = load_payments()
day = date(2026, 8, 23)
revenue(payments, day, day)
```

Restart & Run All даёт `20038.0` за 23 августа и `18246.0` за 16-е — и даёт это при любом порядке запуска.

## Шаг 2. Команда `prime report --date` · `step-2`

Чтобы расчёт запускал планировщик, нужна команда, которую можно набрать в терминале. Делаем её
стандартным модулем `argparse` — он есть в Python, ставить ничего не надо.

Сначала договоримся о дате. **Дата отчёта** — день, когда отчёт читают. Описывает он вчерашний день
и неделю, которая вчера закончилась: за сегодня данных ещё нет. Это правило из раздела 2 итогового проекта.

`src/prime/cli.py`:

```python
def main() -> None:
    parser = argparse.ArgumentParser(prog="prime", description="Мониторинг подписки ПРАЙМ")
    commands = parser.add_subparsers(dest="command", required=True)

    report_cmd = commands.add_parser("report", help="отчёт за одну дату")
    report_cmd.add_argument(
        "--date", type=date.fromisoformat, required=True, help="дата отчёта, ГГГГ-ММ-ДД"
    )

    args = parser.parse_args()
    if args.command == "report":
        print(report.format_report(report.build_day(args.date)))
```

Сверху вниз: создаём разборщик аргументов, заводим в нём команду `report` с обязательным `--date`,
разбираем то, что набрали в терминале, и вызываем расчёт. `type=date.fromisoformat` превращает строку
в дату ещё до нашего кода — и сам ругается, если дата кривая.

Сам расчёт отчёта лежит рядом, в `src/prime/report.py`: `build_day` собирает показатели в словарь,
`format_report` превращает словарь в текст. Командная строка ничего не считает — только разбирает аргументы.

Чтобы команда называлась `prime`, в `pyproject.toml` одна строка:

```toml
[project.scripts]
prime = "prime.cli:main"
```

Запускаем:

```bash
uv run prime report --date 2026-08-24
```

```text
Загружено: 35936 платежей, 3793 подписок
ПРАЙМ, отчёт на 24.08.2026 — данные за 23.08.2026, UTC
  выручка за день        20 038,00 ₽
  выручка за 7 дней     162 051,00 ₽
  новых подписок                 5
```

В первый раз uv ещё напишет `Building prime-workshop` — он пересобрал пакет, потому что в `pyproject.toml`
появилась команда. Так и должно быть.

Дата в привычном русском виде не пройдёт:

```bash
uv run prime report --date 24.08.2026
```

```text
usage: prime report [-h] --date DATE
prime report: error: argument --date: invalid fromisoformat value: '24.08.2026'
```

И `uv run prime --help` теперь показывает, что команда умеет.

**Про зависимости.** Загляните в `pyproject.toml`: pandas и python-dotenv — в `dependencies`, без них
отчёт не посчитается. JupyterLab — в группе `dev`: он нужен вам для исследования, а серверу, который
запускает отчёт, — нет. Точные версии всего этого записаны в `uv.lock`, поэтому `uv sync` у вас, у меня
и на сервере ставит одно и то же.

## Шаг 3. Настройки и секреты — в `.env` · `step-3`

Где лежат данные, какой токен у бота, какой пароль от базы — всё это у каждой машины своё. Если вписать
это в код, код перестанет работать у соседа, а пароль уедет в git вместе с кодом. Поэтому настройки живут
в файле `.env`, который в git не попадает, а в коде — только значения по умолчанию.

Пароль, попавший в репозиторий, — это инцидент, а не мелочь: удалить его из истории git почти невозможно,
его считают скомпрометированным и меняют. Дешевле не допускать.

`src/prime/config.py`:

```python
@dataclass(frozen=True)
class Settings:
    data_dir: Path
    # repr=False: токен не печатается, даже если напечатать настройки целиком
    telegram_token: str = field(repr=False)


def load_settings() -> Settings:
    load_dotenv(ROOT / ".env")
    return Settings(
        data_dir=ROOT / os.getenv("PRIME_DATA_DIR", "data"),
        telegram_token=os.getenv("TELEGRAM_TOKEN", ""),
    )
```

Сверху вниз: описываем, какие настройки бывают; `load_dotenv` читает `.env` в переменные окружения;
`os.getenv` берёт значение или подставляет значение по умолчанию. Настройки собраны в один объект,
и дальше функции получают его параметром, а не лезут в `.env` сами.

Заводим свой `.env` из образца и вписываем в него выдуманный токен — например, `TELEGRAM_TOKEN=7000000000:AAH-fake-token-for-demo`:

```bash
cp .env.example .env
```

Проверьте глазами, что `.env` не попадёт в коммит: `git status` про него молчит, потому что он записан
в `.gitignore`.

```bash
uv run prime report --date 2026-08-24
```

```text
Настройки: Settings(data_dir=PosixPath('…/prime-l9-workshop/data'))
Загружено: 35936 платежей, 3793 подписок
```

Токена в напечатанных настройках нет — это сделал `repr=False`. Без него токен оказался бы на экране,
а на следующем шаге — в журнале. На Windows путь будет вида `WindowsPath('C:/…/data')`.

## Шаг 4. Журнал вместо `print` · `step-4`

Отчёт по расписанию запускается в семь утра, когда терминала перед вами нет. Если что-то пошло не так,
единственный свидетель — журнал. Поэтому служебные сообщения уходят в файл `logs/prime.log` со временем
и уровнем, а в терминал попадают только предупреждения и ошибки.

`src/prime/cli.py`:

```python
def setup_logging(log_file: Path) -> None:
    """Подробности — в файл. В терминал — только предупреждения и ошибки."""
    log_file.parent.mkdir(exist_ok=True)
    to_file = logging.FileHandler(log_file, encoding="utf-8")
    to_file.setLevel(logging.INFO)
    to_screen = logging.StreamHandler()
    to_screen.setLevel(logging.WARNING)
    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s %(levelname)-7s %(name)s: %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S",
        handlers=[to_file, to_screen],
    )
```

Сверху вниз: создаём папку для журнала; заводим два «приёмника» — файл, куда идёт всё от INFO и выше,
и экран, куда идёт только WARNING и ERROR; задаём формат строки: время, уровень, кто пишет, сообщение.

В остальных модулях `print` заменён на `log.info(...)`, а весь запуск обёрнут так, чтобы ошибка
тоже попала в журнал:

```python
    try:
        ...
    except Exception:
        log.exception("Запуск упал")
        sys.exit(1)
```

Запускаем тот же отчёт — в терминале остался только сам отчёт:


```text

  выручка за день        20 038,00 ₽
  выручка за 7 дней     162 051,00 ₽
```

## Шаг 5. `prime replay`: учебное время и сбой посреди дня · `step-5`

Новых данных в базе ПРАЙМ не появляется, поэтому ежедневную работу мы проигрываем: каждый запуск
`prime replay` берёт следующий день истории. Какой день обработан последним, система помнит
в файле `state/replay.json`. Пропущенный запуск день не теряет: следующий начнёт с первого необработанного.

Результат каждого дня записывается строкой в `out/daily.csv`. И тут два правила, без которых запуск
по расписанию рано или поздно сломается.

1. **Повторный запуск того же дня заменяет строку, а не дописывает вторую.** Иначе после любого сбоя
   день задвоится, и выручка за неделю вырастет на ровном месте.
2. **Файл пишется целиком во временный и подменяет старый одной операцией.** Если программа упадёт
   посреди записи, старый файл останется целым, а не обрезанным наполовину.

`src/prime/results.py`:

```python
def write_atomic(path: Path, text: str) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    tmp = path.with_name(path.name + ".tmp")
    tmp.write_text(text, encoding="utf-8")
    os.replace(tmp, path)  # либо старый файл, либо новый — половины не бывает


def save_day(path: Path, row: dict) -> None:
    """Записать показатели дня. Строка за ту же дату отчёта заменяется."""
    table = pd.DataFrame([row])
    if path.exists():
        old = pd.read_csv(path)
        table = pd.concat([old[old["report_date"] != row["report_date"]], table])
    write_atomic(path, table.sort_values("report_date").to_csv(index=False))
```

Сверху вниз в `save_day`: делаем таблицу из одной новой строки; если файл уже есть, читаем его, выкидываем
из него строку за эту же дату и приклеиваем новую; записываем всё через `write_atomic`.

А вот порядок действий в `src/prime/replay.py` — на нём всё и держится:

```python
    results.save_day(settings.out_dir / "daily.csv", row)
    if fail:
        # Учебный сбой ровно в худшем месте: строка уже записана, отметки о дне ещё нет
        raise RuntimeError("учебный сбой: результат записан, отметка о дне — нет")
    results.mark_done(settings.state_file, report_date)
```

Сначала результат, потом отметка «день сделан». Если упадём между ними, день просто пересчитается.
Флаг `--fail` — учебный: он роняет программу ровно в этом месте.

Проигрываем два дня, потом падаем на третьем:

```bash

uv run prime replay
uv run prime replay --fail
```

```text

```

```text

```

```text

```

Что осталось на диске:


## Шаг 6. По расписанию · `step-6`

Осталось, чтобы `prime replay` запускался сам. На macOS и Linux для этого есть cron, на macOS ещё launchd,
на Windows — Планировщик заданий. Готовые заготовки лежат в папке `schedule/`. Сегодня я их показываю,
а включаете вы дома: ставить задачу в планировщик на паре не нужно.

Строка для cron (`crontab -e`):

```cron
* * * * * cd /ПУТЬ/К/prime-l9-workshop && /ПУТЬ/К/uv run prime replay >> logs/cron.log 2>&1
```

Пять звёздочек — «каждую минуту»: так за несколько минут видно неделю учебного времени. В жизни отчёт
раз в сутки, например `0 7 * * *` — в 7:00.

Почему путь к uv написан полностью и зачем `cd`. Cron запускает команду не из вашего терминала, а в почти
пустом окружении: он не знает ни вашего `PATH`, ни папки проекта. Вот как он видит мир:

```bash
env -i HOME="$HOME" /bin/sh -c 'uv --version'
```

```text
/bin/sh: uv: command not found
```

Ваш терминал uv знает, а cron — нет. Полный путь подскажет `which uv`. Всё, что упало до того, как
программа открыла свой журнал (как этот «command not found»), попадёт в `logs/cron.log` — туда смотрим первым делом,
если расписание молчит.

Для Windows команда для Планировщика заданий — в `schedule/README.md`.

Облачные планировщики вроде GitHub Actions тоже умеют запускать по расписанию, но пароль от учебной базы
им отдавать нельзя без согласования: так записано в задании итогового проекта.

И главное: выключите задачу, когда наиграетесь. Снимок кончается 30 августа, дальше `replay` пишет
в журнал предупреждение — но планировщик будит его каждую минуту, пока вы его не выключите.

## Если что-то пошло не так

| Что видно | Что делать |
|---|---|
| `uv sync` долго качает пакеты или падает без сети | на паре — смотреть на экран; дома `uv sync` ещё раз. Версии те же, что в вашем `prime-monitor`, так что обычно всё берётся из кэша |
| `error: Your local changes … would be overwritten` | вы забыли `-f`: `git checkout -f step-N` |
| `prime: command not found` или `No such command` | запускайте через `uv run prime …`, а не просто `prime …` |
| В ноутбуке `ModuleNotFoundError: No module named 'prime'` | ядро не из этого проекта: перезапустите `uv run jupyter lab` из папки репозитория |
| Числа не совпадают со страницей | проверьте, что стоите на нужном шаге: `git describe --tags` |
