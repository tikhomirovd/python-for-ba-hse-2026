# Часть 1. Внешние API

## Как устроен запрос

Когда программа идёт в API, она делает то же, что браузер, только без картинок. Отправляет **запрос**:
метод (почти всегда `GET` — «дай»), адрес и параметры после знака `?`. Получает **ответ** из трёх частей:
код, заголовки и тело.

Код — первое, на что смотрим. Его первая цифра говорит, кто виноват и стоит ли пробовать ещё раз:

| Код | Что значит | Повторять? |
|---|---|---|
| `200` | всё хорошо | — |
| `400`, `404` | вы спросили не то: опечатка в адресе, неверный параметр | нет: ответ будет тем же |
| `401`, `403` | нет прав или неверный ключ | нет: сначала разберитесь с ключом |
| `429` | вы спрашиваете слишком часто | да, но подождав столько, сколько попросил сервер |
| `500`, `502`, `503`, `504` | сломалось на стороне сервера | да, через паузу |

Тело приходит текстом в одном из двух форматов. **JSON** — словари и списки, как в Python: так отвечает
Мосбиржа. **XML** — вложенные теги, как в HTML: так отвечает Банк России.

## Шаг 1. Один запрос · `step-1`

Прежде чем писать загрузчик, посмотрим глазами, что вообще приходит. Это обычный скрипт без всякого
пакета: так начинается знакомство с любым новым API.

`scripts/one_request.py`, главное:

```python
url = "https://iss.moex.com/iss/history/engines/stock/markets/index/securities/IMOEX.json"
params = {"from": "2026-08-28", "till": "2026-08-28", "iss.meta": "off"}

response = requests.get(url, params=params, timeout=10)

print("Код:   ", response.status_code)
print("Тип:   ", response.headers["Content-Type"])
data = response.json()
```

Сверху вниз: адрес — это история индекса МосБиржи, параметры просят один день, 28 августа 2026-го.
`requests.get` сам склеит адрес с параметрами. `timeout=10` — не ждать ответа дольше десяти секунд;
без него программа при зависшем сервере будет ждать вечно, и об этом подробно на шаге 4.
`response.json()` превращает тело ответа в словарь Python.

```bash
uv run python scripts/one_request.py
```

```text
Адрес:  https://iss.moex.com/iss/history/engines/stock/markets/index/securities/IMOEX.json?from=2026-08-28&till=2026-08-28&iss.meta=off
Код:    200
Тип:    application/json; charset=utf-8
Размер: 614 байт
Блоки:  ['history', 'history.cursor']
Колонки: 20 штук, строк: 1
Строка:  {'TRADEDATE': '2026-08-28', 'OPEN': 2113.27, 'CLOSE': 2114.93}

Неверный адрес:  код 404
Неверный тикер:  код 200 — строк в ответе: 0
```

Три вещи, которые стоит отсюда унести.

**JSON у Мосбиржи — это не список словарей.** Названия колонок лежат отдельно, строки отдельно.
Чтобы получить привычную запись «колонка → значение», их склеивают: `dict(zip(columns, row))`,
а для таблицы — `pd.DataFrame(data, columns=columns)`.

**Код ответа говорит не обо всех ошибках.** На неверный адрес сервер честно отвечает `404`.
А на несуществующий тикер — `200` и пустую таблицу. Программа, которая проверяет только код,
решит, что всё хорошо. Пустой ответ надо проверять отдельно.

**Заголовок `Content-Type` говорит, как читать тело:** здесь JSON в кодировке UTF-8.
У Банка России на следующем шаге будет другая кодировка.

## Шаг 2. Курсы ЦБ на дату · `step-2`

Банк России каждый рабочий день публикует официальные курсы валют. Для мониторинга ПРАЙМ это фон:
например, видно, совпало ли падение выручки с резким движением рубля.

С этого шага в проекте появляется **один вход в сеть** — функция `get` в `src/prime/fetch.py`.
Все запросы идут через неё, поэтому тайм-аут, а на шаге 4 и повторы, настраиваются в одном месте.

```python
def get(url: str, params: dict | None = None) -> bytes:
    """Скачать ответ целиком."""
    if os.environ.get("PRIME_OFFLINE") == "1":
        return _read_recorded(url, params)

    response = requests.get(url, params=params, headers=HEADERS, timeout=TIMEOUT)
    response.raise_for_status()  # 4xx и 5xx — исключение, а не тихий пустой ответ
    _record(url, params, response.content)
    return response.content
```

Сверху вниз: в офлайн-режиме берём записанный ответ с диска. Иначе делаем запрос с тайм-аутом
`(3, 10)` — три секунды на соединение и десять на ответ. `raise_for_status()` превращает код 4xx или 5xx
в исключение: лучше упасть с понятной ошибкой, чем пойти дальше с пустыми данными. Возвращаем
байты, а не текст: как их читать, решает тот, кто знает формат.

Сам разбор — в `src/prime/sources/cbr.py`:

```python
def rates_on(day: date) -> pd.DataFrame:
    """Курсы на день day: сколько рублей стоит одна единица валюты."""
    content = get(URL, {"date_req": day.strftime("%d/%m/%Y")})

    # Отдаём парсеру байты, а не текст: кодировку windows-1251
    # он прочитает сам из первой строки ответа.
    root = ET.fromstring(content)
    cbr_date = datetime.strptime(root.get("Date"), "%d.%m.%Y").date()

    rows = []
    for valute in root.iter("Valute"):
        currency = valute.findtext("CharCode")
        if currency in CURRENCIES:
            rate = valute.findtext("VunitRate").replace(",", ".")  # у ЦБ запятая
            rows.append({"on_date": day, "cbr_date": cbr_date, "currency": currency, "rate": float(rate)})
    return pd.DataFrame(rows)
```

Сверху вниз: ЦБ ждёт дату в формате `21/08/2026`. Ответ — XML в старой кириллической кодировке
windows-1251, и первая строка ответа так и говорит: `encoding="windows-1251"`. Поэтому отдаём парсеру
`xml.etree` байты, он прочитает кодировку сам. Дальше проходим по всем тегам `Valute` и оставляем доллар,
евро и юань. Курс записан с запятой, `92,57`, а `float` понимает только точку — меняем.
`VunitRate` — курс за одну единицу валюты: у некоторых валют ЦБ публикует курс за 10 или 100 единиц.

```bash
uv run prime rates --date 2026-08-21
uv run prime rates --date 2026-08-24
```

```text
   on_date   cbr_date currency    rate
2026-08-21 2026-08-21      USD 83.3550
2026-08-21 2026-08-21      EUR 96.7335
2026-08-21 2026-08-21      CNY 12.4057

   on_date   cbr_date currency    rate
2026-08-24 2026-08-22      USD 82.9211
2026-08-24 2026-08-22      EUR 96.8601
2026-08-24 2026-08-22      CNY 12.3343
```

**Попросили понедельник, 24 августа, — ЦБ ответил курсом с датой субботы, 22-го.** Это не ошибка:
курс, установленный в пятницу, действует в субботу, воскресенье и понедельник, и ЦБ честно пишет,
с какой даты он действует. Поэтому храним обе даты. `on_date` — день, о котором спрашивали: по ней
будем соединять с метриками ПРАЙМ. `cbr_date` — что ответил источник: по ней видно, что курс
на выходные не новый.

> **Для итогового проекта.** Внешние показатели должны соответствовать дате отчёта, а не сегодняшнему дню.
> Отчёт за 24 августа берёт курс `on_date = 2026-08-24`, а не тот, что ЦБ отдаёт сегодня.

## Шаг 3. Постраничная выдача · `step-3`

Многие API не отдают всё за один раз. Мосбиржа на один запрос возвращает не больше 100 строк,
а торговых дней с января 2025-го по август 2026-го — больше четырёхсот. Остальное лежит на следующих
страницах, и номер первой строки страницы задаёт параметр `start`.

Правило забора самое простое: **просим страницу за страницей, пока не придёт пустая.**

`src/prime/sources/moex.py`:

```python
def index_history(ticker: str, start: date, end: date) -> pd.DataFrame:
    """Дневные закрытия индекса за период: все страницы подряд."""
    pages = []
    offset = 0
    while True:
        params = {
            "from": start.isoformat(),
            "till": end.isoformat(),
            "start": offset,
            "iss.meta": "off",
            "history.columns": "TRADEDATE,CLOSE",
        }
        block = json.loads(get(URL.format(ticker=ticker), params))["history"]
        log.info("start=%d: %d строк", offset, len(block["data"]))
        if not block["data"]:  # пустая страница — дальше ничего нет
            break
        pages.append(pd.DataFrame(block["data"], columns=block["columns"]))
        offset += len(block["data"])
    ...
    history = pd.concat(pages, ignore_index=True)
```

Сверху вниз: `history.columns` просит только две нужные колонки из двадцати, ответ сразу становится
в десять раз меньше. Каждую страницу превращаем в таблицу — колонки и строки склеиваем, как на шаге 1.
`offset` сдвигаем на столько строк, сколько реально пришло, а не на 100: если сервер однажды начнёт
отдавать по 50, код продолжит работать. Пустая страница — выходим. В конце склеиваем страницы
в одну таблицу.

```bash
uv run prime index --from 2025-01-06 --till 2026-08-30
```

```text
INFO start=0: 100 строк
INFO start=100: 100 строк
INFO start=200: 100 строк
INFO start=300: 100 строк
INFO start=400: 19 строк
INFO start=419: 0 строк
IMOEX: 419 торговых дней
trade_date   close
2025-01-06 2816.26
2026-08-28 2114.93
```

Шесть запросов, последний — пустой. Индекс за это время упал с 2816 до 2115 пунктов, на четверть.

Мосбиржа присылает и блок `history.cursor` с общим числом строк, `TOTAL: 419`. По нему можно было бы
не делать шестой запрос. Но курсор есть не у всех API, а правило «пока не пусто» работает везде.
Другие API вместо номера строки выдают в ответе ссылку или метку на следующую страницу — логика та же:
идём по ней, пока она есть.

## Шаг 4. Тайм-аут и повторы · `step-4`

Сеть ломается. Сервер перегружен и отвечает `503`, просит не торопиться — `429`, или просто молчит.
Загрузчик, который в три часа ночи упал из-за одной неудачной попытки, — это отчёт, который утром
не пришёл.

Повторять надо с умом. Что повторяем, а что нет, — по таблице в начале страницы: `429` и `5xx` —
да, `4xx` — нет, потому что неверный запрос останется неверным. Ждём между попытками всё дольше:
1, 2, 4 секунды. Если сервер прислал заголовок `Retry-After`, ждём столько, сколько он просит.

В `fetch.get` один запрос превращается в цикл:

```python
    for attempt in range(1, ATTEMPTS + 1):
        try:
            response = requests.get(url, params=params, headers=HEADERS, timeout=TIMEOUT)
        except (requests.ConnectionError, requests.Timeout) as error:
            if attempt == ATTEMPTS:
                raise
            wait = 2 ** (attempt - 1)
            log.warning("попытка %d: %s, ждём %d с", attempt, type(error).__name__, wait)
        else:
            if response.status_code not in RETRY_STATUSES or attempt == ATTEMPTS:
                response.raise_for_status()  # 4xx — ошибка сразу, повтор не поможет
                _record(url, params, response.content)
                return response.content
            retry_after = response.headers.get("Retry-After", "")
            wait = int(retry_after) if retry_after.isdigit() else 2 ** (attempt - 1)
            log.warning("попытка %d: код %d, ждём %d с", attempt, response.status_code, wait)
        time.sleep(wait)
```

Сверху вниз: до четырёх попыток. Если соединиться не удалось или ответ не пришёл за отведённое время,
ловим исключение и ждём `2 ** (attempt - 1)` секунд: 1, 2, 4. На последней попытке исключение
пропускаем наружу — пусть вызывающий код узнает, что источник недоступен. Если ответ пришёл,
смотрим код: всё, кроме `429` и `5xx`, сразу отдаём или превращаем в ошибку. Иначе ждём —
сколько просит сервер или сколько решили сами — и пробуем снова. Каждая неудача пишется в журнал.

Проверить это на настоящих ЦБ и Мосбирже нельзя: они, к счастью, отвечают. Поэтому `scripts/retry_demo.py`
поднимает прямо на вашем компьютере капризный сервер, который отвечает со второго-третьего раза:

```bash
uv run python scripts/retry_demo.py
```

```text
== /flaky: сервер дважды отвечает 503
WARNING попытка 1: код 503, ждём 1 с
WARNING попытка 2: код 503, ждём 2 с
ответ «ok» с 3-го запроса, 3 с

== /busy: сервер просит подождать: 429 и Retry-After: 2
WARNING попытка 1: код 429, ждём 2 с
ответ «ok» с 2-го запроса, 2 с

== /missing: такого адреса нет: 404
ошибка сразу, запросов: 1 — 404 Not Found

== /slow: первый ответ идёт дольше тайм-аута
WARNING попытка 1: ReadTimeout, ждём 1 с
ответ «ok» с 2-го запроса, 2 с
```

На работе такой цикл обычно не пишут руками. У `requests` есть встроенный механизм повторов
(`urllib3.Retry`), есть библиотека `tenacity`, которая добавляет повторы к любой функции одной строкой
сверху. Мы написали свой, чтобы было видно, что у них внутри. Одна вещь, которой у нас нет:
когда клиентов много, к паузе добавляют случайную добавку, чтобы все не постучались в сервер
в одну и ту же секунду.

**Повторять безопасно только то, что можно повторить.** `GET` только читает: десять одинаковых
запросов курса дадут тот же курс. А запрос, который что-то делает, — например, отправляет сообщение
в Telegram, — при повторе после тайм-аута может отправить его дважды: ответ не пришёл, но сообщение
уже ушло. Для таких запросов повторы ставят осторожнее.

## Шаг 5. Повторный запуск без дублей · `step-5`

В итоговом проекте один и тот же день будет обрабатываться не раз: `backfill` пересчитывает месяц,
`replay` после сбоя возвращается ко вчерашней дате. Если каждый запуск просто дописывает строки
в хранилище, дни задвоятся.

И задвоение не бросается в глаза. Вот что будет, если дважды дописать историю индекса в таблицу
без ключа:

```text
после 1-го запуска: 419 строк
после 2-го запуска: 838 строк
средний close не изменился: 2728.61 и 2728.61
```

Среднее осталось прежним, на графике дубликатов не видно. Сломается сумма, число дней, доля —
а заметят это не сразу.

Лечится ключом. У каждой таблицы в `src/prime/store.py` есть **первичный ключ** — набор колонок,
которые не могут повториться. Для истории индекса это тикер и дата:

```python
connection.executemany(
    """
    insert into index_history (ticker, trade_date, close)
    values (?, ?, ?)
    on conflict (ticker, trade_date) do update set close = excluded.close
    """,
    rows,
)
```

Сверху вниз: вставляем строки по одной, подставляя значения на место знаков `?`. Если строка с таким же
тикером и датой уже есть, `on conflict … do update` не добавляет вторую, а обновляет цену в существующей.
Такую запись называют **идемпотентной**: сколько раз ни запусти, результат как после одного запуска.
Хранилище — файл SQLite `data/external.sqlite`, он закрыт в `.gitignore`.

```bash
uv run prime index --from 2025-01-06 --till 2026-08-30 --save
uv run prime index --from 2025-01-06 --till 2026-08-30 --save
```

```text
...
INFO строк в таблице index_history: 419
...
INFO строк в таблице index_history: 419
```

С курсами то же: `uv run prime rates --date 2026-08-24 --save` дважды подряд оставляет в `fx_rates`
три строки. Ключ там — `on_date` и валюта, то есть день, о котором спрашивали, а не дата из ответа ЦБ:
иначе понедельник перезаписал бы субботу.

## Шаг 6. Токен и журнал · `step-6`

Открытые API ЦБ и Мосбиржи ключа не требуют. Большинство других — требуют: так сервис знает, кто
к нему пришёл, сколько запросов разрешить и кому выставить счёт. В итоговом проекте такой ключ у вас
будет: токен Telegram-бота.

Где он живёт, вы уже знаете: в `.env`, который не попадает в git. Но ключ может утечь и без git.

Обычно ключ передают одним из трёх способов:

- **в заголовке запроса**, например `Authorization: Bearer <ключ>`. Это лучший вариант: заголовки
  почти никто не записывает в журналы;
- **в параметрах адреса**, `?api_key=<ключ>`. Хуже: адрес пишут в журналы и сервер, и ваша программа;
- **прямо в пути адреса**. Так устроен Telegram: `https://api.telegram.org/bot<токен>/sendMessage`.

Третий случай — ловушка. Бот молчит, вы включаете подробный журнал, чтобы понять почему,
и библиотека `urllib3`, на которой стоит `requests`, на уровне `DEBUG` записывает адрес каждого запроса.
Вместе с токеном.

`scripts/leak_demo.py` поднимает на вашем компьютере сервер, похожий на Telegram, и отправляет
ему запрос с ненастоящим токеном из `.env`. Два раза: с журналом «как все включают» и с настройкой
проекта.

```bash
uv run python scripts/leak_demo.py
```

```text
== basicConfig(level=DEBUG)
Токен в журнале: да
    DEBUG:urllib3.connectionpool:http://127.0.0.1:59305 "GET /bot123456789:AAFake-token-for-the-workshop-only/getMe HTTP/1.1" 200 None

== setup_logging(DEBUG) из prime/log.py
Токен в журнале: нет
```

Номер порта у вас будет другим. Разница между двумя вариантами — одна строка в `src/prime/log.py`:

```python
    # urllib3 (на нём стоит requests) на уровне DEBUG пишет адрес каждого
    # запроса. Если токен стоит в адресе, как у Telegram, он уедет в журнал.
    logging.getLogger("urllib3").setLevel(logging.WARNING)
```

Наш собственный журнал остаётся подробным, а `urllib3` пишет только предупреждения и ошибки.

**Если ключ всё-таки утёк** — в журнал, в git, в чат, — его не прячут, а **отзывают и заменяют**.
Удалить строку из файла мало: копия журнала уже могла уехать в бэкап, коммит — в чужой клон.
У Telegram-бота это команда `/revoke` у [@BotFather](https://t.me/BotFather): старый токен перестаёт
работать, вы получаете новый и кладёте его в `.env`. Там, где ключи живут долго, их и без утечки
меняют по расписанию — **ротируют**: выпускают новый, переключают программу, отзывают старый.

Есть и третий вид доступа — **OAuth**. Он нужен, когда программа действует от имени человека: например,
пишет в вашу Google-таблицу. Вы один раз подтверждаете доступ в браузере, программа получает
токен на ограниченное время и умеет его продлевать. В курсе он может понадобиться, если будете выгружать
результат в Google-таблицу (тема 11).

## Можно ли так собирать данные

Открытый API — это приглашение: владелец сам решил, что данными можно пользоваться. Но и у него
есть правила.

- **Условия использования.** У каждого API они свои: где-то запрещено коммерческое использование,
  где-то нужно указывать источник. Прочитайте их до того, как ставить загрузку на расписание.
- **Не чаще, чем нужно.** Курс ЦБ меняется раз в день — спрашивать его каждую минуту незачем.
  Если сервер отвечает `429`, это просьба, а не приглашение повторить в цикле без пауз.
- **Представьтесь.** Наш загрузчик отправляет заголовок `User-Agent: prime-l10-workshop/0.1`.
  Если что-то пойдёт не так, владелец увидит, чья это программа, а не заблокирует всех подряд.
- **Скачивать страницы сайта** вместо API (это называют скрейпингом) — отдельная история: для этого
  есть файл `robots.txt`, где сайт пишет, что можно забирать, и условия сайта, которые могут это запрещать.
- **Персональные данные** — то, по чему можно узнать человека: имена, телефоны, профили. Собирать их
  без законного основания нельзя, даже если они открыто лежат на странице: это закон о персональных
  данных, 152-ФЗ. Для мониторинга ПРАЙМ они и не нужны.

# Часть 2. Хранилища — смотрим на экран

Дальше — с проектора. Все числа сняты на копии учебной базы: PostgreSQL 18, таблица `prime.payments`,
3 147 409 платежей. Повторять дома на учебном сервере не нужно: несколько выгрузок миллионов строк
от каждого из нас сервер не выдержит.

## 1. f-строка против параметра

Запрос из Python — это строка. Самое очевидное — подставить в неё значение f-строкой. Пока значение
пишете вы сами, всё работает:

```python
channel = "organic"
sql = f"select count(*) as clients from prime.clients where acquisition_channel = '{channel}'"
pd.read_sql(sql, engine)
```

```text
   clients
0   117952
```

Но если значение пришло снаружи — из конфигурации, из чужого файла, из поля формы, —
оно может изменить сам запрос. Одна кавычка, и условие становится другим:

```python
channel = "x' or '1'='1"
```

```text
select count(*) as clients from prime.clients where acquisition_channel = 'x' or '1'='1'
   clients
0   500000
```

Вместо «клиентов канала x», которых нет, получили всех полмиллиона: `'1'='1'` верно для любой строки.
Здесь это безобидно, а на базе, где запрос что-то меняет, так удаляют таблицы. Приём называется
**SQL-инъекция**.

Параметр решает это раз и навсегда. Значение передаётся в базу отдельно от текста запроса, и база
понимает его как значение, а не как кусок SQL:

```python
query = text("select count(*) as clients from prime.clients where acquisition_channel = :channel")
pd.read_sql(query, engine, params={"channel": channel})
```

```text
   clients
0        0
```

Та же строка `x' or '1'='1` теперь ищется как название канала — и такого канала нет.
С `"organic"` этот же запрос даёт 117 952. В итоговом проекте подстановка f-строкой в SQL запрещена.

## 2. Что происходит с типами на границе

База и pandas хранят данные по-разному, и на границе каждый тип во что-то превращается.
Иногда — не в то, что вы ждёте.

```python
payments = pd.read_sql(
    "select payment_id, paid_at, amount, status from prime.payments limit 1000",
    engine,
)
payments.dtypes
```

```text
payment_id                 object
paid_at       datetime64[us, UTC]
amount                    float64
status                        str
```

| В базе | В pandas | На что смотреть |
|---|---|---|
| `uuid` | `object`, внутри объекты `uuid.UUID` | каждое значение — отдельный объект Python, это тяжело для памяти; сравнение с текстом `'…'` молча даёт `False` |
| `timestamptz` | `datetime64[us, UTC]` | время приходит в UTC; в местное переводить самим, как на теме 05 |
| `numeric` | `float64` | точные деньги базы стали числами с плавающей точкой: суммы сверяем с допуском, как на С3 |
| `text` | `str` | всё как ждали |

## 3. Целиком, порциями или в базе

Таблица платежей — три миллиона строк. Нужна дневная выручка: 600 чисел. Четыре способа её получить:

```python
SQL_ROWS = "select payment_id, paid_at, amount, status from prime.payments"


def daily(frame: pd.DataFrame) -> pd.Series:
    ok = frame[frame["status"] == "success"]
    return ok.groupby(ok["paid_at"].dt.floor("D"))["amount"].sum()


# 1. Выгрузить всё и посчитать в pandas
def variant_whole(engine) -> pd.Series:
    payments = pd.read_sql(SQL_ROWS, engine)
    return daily(payments)


# 2. Читать порциями по 200 000 строк и складывать дневные суммы порций
def variant_chunks(engine) -> pd.Series:
    parts = [daily(chunk) for chunk in pd.read_sql(SQL_ROWS, engine, chunksize=200_000)]
    return pd.concat(parts).groupby(level=0).sum()


# 3. То же, но попросить базу отдавать строки по мере чтения
def variant_stream(engine) -> pd.Series:
    with engine.connect().execution_options(stream_results=True) as connection:
        parts = [daily(chunk) for chunk in pd.read_sql(SQL_ROWS, connection, chunksize=200_000)]
    return pd.concat(parts).groupby(level=0).sum()


# 4. Посчитать в базе и выгрузить готовый ответ
SQL_DAILY = """
    select date_trunc('day', paid_at) as day, sum(amount) as revenue
    from prime.payments
    where status = 'success'
    group by 1
    order by 1
"""


def variant_database(engine) -> pd.Series:
    return pd.read_sql(SQL_DAILY, engine).set_index("day")["revenue"]
```

`daily` оставляет успешные платежи и складывает суммы по дням. Во втором и третьем способе
она работает на каждой порции отдельно; день может попасть в две соседние порции, поэтому
в конце суммы порций складываются ещё раз по дню. Каждый способ мерили в отдельном процессе Python.

| Способ | Время, с | Сколько памяти добавилось, МБ | Ответ |
|---|---:|---:|---|
| целиком | 3,5 | 2 245 | 880 737 565,00 ₽ за 600 дней |
| `chunksize=200_000` | 3,5 | 718 | то же |
| `chunksize` + `stream_results` | 4,1 | 297 | то же |
| `group by` в базе | 0,7 | 3 | то же |

**Ответ у всех четырёх одинаковый до копейки, а память различается в сотни раз.**

Второй способ — тихая ловушка. `chunksize` обещает «по 200 000 строк», и pandas правда отдаёт
таблицы по 200 000. Но драйвер базы по умолчанию сначала забирает **весь** результат запроса к себе
в память, а pandas нарезает его уже потом. Порции получились, но драйвер всё равно держит в памяти весь результат: 718 МБ против 297
при настоящем чтении по частям.
Настоящее чтение по частям включает `stream_results=True`: тогда база отдаёт строки по мере того,
как мы их просим.

Но лучший способ — четвёртый, и это не новость: «считает база, а не ноутбук» — правило с первого модуля.
Порции нужны, когда агрегат в SQL не выразить и строки действительно нужны в Python.

## 4. Строки против колонок: PostgreSQL и ClickHouse

Тот же агрегат — дневная выручка по успешным платежам — в пяти движках:

| Движок | Время, с | Ответ |
|---|---:|---|
| PostgreSQL 18, таблица `prime.payments` | 0,71 | 880 737 565,00 ₽, 600 дней |
| ClickHouse (chdb), `payments.parquet` | 0,04 | то же, совпадает по каждому дню |
| DuckDB, `payments.parquet` | 0,05 | то же |
| polars, `payments.parquet` | 0,01 | то же |
| pandas, `read_parquet` трёх колонок | 0,07 | то же |

ClickHouse здесь встроенный (библиотека `chdb`) и читает файл Parquet; на семинаре планируем настоящий
сервер ClickHouse. Время — медиана трёх запусков после разогрева. Таблицу PostgreSQL при этом целиком
читал из своего кэша в памяти, а не с диска: дело не в скорости диска.

**Почему разница примерно в 18 раз.** Дело в том, как данные лежат.

PostgreSQL — **строковое хранилище**: строка таблицы лежит целиком, все шесть колонок подряд.
Чтобы сложить `amount`, он проходит по всем строкам целиком — 279 МБ, вместе с двумя идентификаторами
и способом оплаты, которые этому запросу не нужны.

ClickHouse, DuckDB, Parquet — **колоночные**: каждая колонка лежит отдельно. Запросу нужны три колонки
из шести, и движок читает только их:

```text
Parquet: весь файл — 241 МБ, по колонкам:
    payment_id       107.3 МБ
    subscription_id  106.9 МБ
    paid_at           24.8 МБ  ← нужна запросу
    amount             0.8 МБ  ← нужна запросу
    status             0.3 МБ  ← нужна запросу
    payment_method     0.8 МБ
Колоночному движку нужно 26 МБ из 241 МБ — 11%
```

И это ещё не всё. Колонка `status` — три миллиона строк, а занимает 0,3 МБ: значений всего три,
и одинаковые значения подряд сжимаются почти в ноль. В строковом хранилище так не сжать: рядом
со статусом лежит уникальный идентификатор. Наконец, колоночный движок обрабатывает колонку большими
пачками значений за раз, а не строку за строкой.

Наглядно, по шагам, — на схеме [`хранилища.html`](хранилища.html). На GitHub откроется её код:
скачайте файл кнопкой **Download raw file** и откройте в браузере.
Числа на схеме чуть другие: там измерена таблица внутри самого ClickHouse, где идентификаторы хранятся
в типе UUID, а здесь — колонки файла Parquet. Вывод тот же: для суммы по дням строковому хранилищу
приходится пройти 279 МБ, колоночному хватает примерно десятой части.

**Почему тогда не хранить всё в ClickHouse.** Потому что строковое хранилище выигрывает на другой работе.
Найти один платёж по номеру, поменять статус одной подписки, принять тысячу новых платежей в секунду
так, чтобы ни один не потерялся, — это работа PostgreSQL. Колоночному движку, чтобы собрать одну строку,
надо заглянуть в шесть мест, а менять отдельные строки он не любит. Поэтому в компаниях обычно оба:
приложение пишет в PostgreSQL, а копия данных для аналитики едет в ClickHouse.

Проверили и ещё одну догадку: может, PostgreSQL тормозит из-за точного типа денег `numeric`?
Нет: с `sum(amount::float8)` он считает за 0,77 с, не быстрее.

## 5. Обзорно: файлы Parquet, партиции, polars и DuckDB

**Parquet** — колоночный формат файла. Всё сказанное выше про колонки работает и для файла на диске:
`pd.read_parquet(path, columns=[...])` читает только нужные колонки. Для локального хранилища
итогового проекта это хороший выбор наравне с SQLite.

**Партиции** — та же таблица, разложенная по папкам, например по месяцам:

```text
payments/ — 20 папок: month=2025-01 … month=2026-08
Весь файл:          3 147 409 строк, 0.08 с
Только 2026-08:       191 361 строк, 0.01 с
```

Фильтр `pd.read_parquet(folder, filters=[("month", "==", "2026-08")])` открывает одну папку
из двадцати, остальные даже не трогает. На трёх миллионах строк выигрыш — доли секунды,
на трёх миллиардах — разница между «посчиталось» и «не влезло в память».

**polars и DuckDB** — два способа считать на колоночных данных быстрее pandas.

- **polars** — та же идея таблицы, что в pandas, но вычисления сразу на всех ядрах процессора и ленивые:
  сначала описываете весь расчёт, потом он выполняется целиком и читает только нужное.
- **DuckDB** — встроенная база, как SQLite, только колоночная: пишете SQL прямо по файлу Parquet
  или по таблице pandas.

Когда на них переходить: когда pandas не помещается в память или считает минутами. На данных
ПРАЙМ, где самая большая таблица — восемь миллионов строк (`service_usage`), pandas хватает, и итоговый проект можно
сделать целиком на нём.

## Что унести

- Все запросы — через одну функцию: тайм-аут всегда, повторы только для `429` и `5xx`, пауза растёт.
- Код `200` не значит, что данные есть: пустой ответ проверяйте отдельно.
- Внешние данные храните по дате, о которой спрашивали, и с ключом: повторный запуск не должен дублировать.
- Ключи — в `.env`, токены не попадают в журнал, утёкший ключ отзывают.
- Значения в SQL — только параметрами, считать — в базе.
- Колоночное хранилище читает только нужные колонки, поэтому агрегаты в нём быстрее в десятки раз;
  строковое — для поиска и изменения отдельных строк.
