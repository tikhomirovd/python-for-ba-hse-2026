Git втроём

Как разделить дневной отчёт на задачи, работать параллельно и собрать проверенные изменения в одной ветке main.

Аня считает выручку

Из трёх платежей на 100, 200 и 50 ₽ прошли первые два. Аня возвращает два числа за день — 300 ₽ выручки и 2 успешных платежа.

Борис считает средний платёж

В его ветке уже есть функция Ани. Борис делит выручку на число успешных платежей и получает 300 / 2 = 150 ₽.

Вера собирает сводку

Вера начинает шаблон от main. Когда оба расчёта влиты, она подключает их и сверяет две строки отчёта — «Выручка 300 ₽» и «Средний платёж 150 ₽».

Зависимые задачи

Когда нужна ветка Ани?

Аня уже выложила расчёт числа платежей и отказов по дням. Вера проверяет её PR. Борису нужны эти числа для недельной доли отказов. Он может начать сегодня и отдать свою работу на отдельное ревью.

Как Борису создать ветку и открыть свой PR?
  1. Начните с коммита Ани. Аня отправила свою ветку на GitHub. В своём клоне Борис выполняет команды при чистой рабочей копии. 
    git fetch origin
git switch --no-track -c feature/weekly-rate origin/feature/daily-counts
    Теперь у Бориса есть отдельная локальная ветка с дневными числами. Новые коммиты Ани можно забрать позже.
  2. Покажите Вере недельный расчёт. После своего первого коммита Борис выполняет git push -u origin feature/weekly-rate. На GitHub он открывает PR с base = feature/daily-counts и compare = feature/weekly-rate. Пока PR Ани открыт, Вера уже может смотреть изменения Бориса в Files changed. Слияние PR Бориса оставьте до следующего шага.
  3. После слияния PR Ани перенаправьте PR Бориса в main. В примере команда выбирает Create a merge commit для PR Ани. Борис забирает итог её ревью в свою ветку. 
    git switch feature/weekly-rate
git fetch origin
git merge origin/main
git push
    В открытом PR Борис проверяет поле base. Если там ещё feature/daily-counts, рядом с заголовком нажимает Edit, выбирает main и подтверждает Change base. Вера ещё раз открывает Files changed. Там должны быть только изменения для недельного расчёта. Она сверяет долю с исходными числами, затем команда вливает второй PR. Смена базы PR на GitHub

Как разделить работу?

Если вся команда пишет в одной ветке, готовая выручка может застрять из-за незаконченной сводки. Выберите ситуацию из проекта и решите, что можно влить отдельно, а где сначала нужно договориться с коллегой.

Я написала две функции для выручки. Коллега добавляет третью — отбор по дате только для этой метрики. Сколько веток взять?

От ветки до pull request

Как влить изменения в main

Пройдём путь Ани. Команды выполняйте в терминале из корня своего клона командного репозитория.

01Начните задачу от свежей main

Договоритесь, какой результат должна дать фича. Аня считает выручку за день и число успешных списаний. Борису понадобятся оба результата. Проверьте, что рабочая копия чистая, обновите main и создайте ветку.

git status
git switch main
git pull --ff-only
git switch -c feature/revenue
02Проверьте расчёт и отправьте ветку

Запустите свой расчёт за один день. В исходной таблице payments за тот же день оставьте строки со статусом success и сложите amount. Сверьте две суммы. Используйте границы дня и часовой пояс, которые выбрала команда.

Посмотрите изменения и отправьте расчёт на GitHub. В команде git add подставьте путь к файлу, который вы изменили.

git status --short
git add src/prime/revenue.py
git diff --cached
git commit -m "Рассчитать выручку по успешным платежам"
git push -u origin feature/revenue
03Откройте PR и попросите коллегу проверить

На GitHub откройте Pull requests → New pull request. Выберите base = main (куда вливаем) и compare = feature/revenue (откуда). Нажмите Create pull request.

В описании PR укажите дату, способ запуска и две суммы, которые вы сравнили. Для трёх платежей с нашей схемы подошла бы такая запись. «Расчёт вернул 300 ₽. Вручную получилось 100 + 200 = 300 ₽. Платёж на 50 ₽ отклонён».

Борис открывает Files changed, смотрит, какие статусы попадают в сумму, и повторяет расчёт за указанную дату. Если понадобятся правки, Аня делает новый коммит в этой же ветке и выполняет git push. Изменения появятся в открытом PR.

04Проверьте совместимость и выполните merge

Когда коллега сверил результат и вы учли замечания, нажмите в PR Merge pull request → Confirm merge. На схеме выбран вариант Create a merge commit. Кружок на main показывает, где сошлись две истории.

Если PR зависит от чужого кода, сначала влейте зависимость. Так делает Вера после слияния обеих метрик. С сохранёнными в коммите правками она обновляет свою ветку, подключает реальные расчёты и проверяет сводку целиком.

git switch feature/summary
git fetch origin
git merge origin/main

Сформируйте сводку за одну дату. Сравните обе цифры с отдельными расчётами Ани и Бориса за тот же день. Если они совпали, добавьте изменённые файлы через git add, сделайте коммит и выполните git push. Коллега проверяет итоговый PR Веры перед слиянием.

Что делать, если Git показал конфликт?

Оставайтесь в ветке задачи. Команда git status покажет спорные файлы. Откройте их и найдите блоки между <<<<<<<, ======= и >>>>>>>. Вместе с автором второй правки соберите нужную версию и удалите маркеры.

Например, если вы оба добавили показатель в одну строку сводки, проверьте, что в ней видны и выручка, и средний платёж. Для конфликта в src/prime/summary.py команды будут такими.

git add src/prime/summary.py
git diff --cached
git commit -m "Объединить изменения сводки"
git push
05Обновите main у себя

После слияния на GitHub каждый у себя переключается на main и забирает изменения. Следующую фичу начинайте от обновлённой main.

git switch main
git pull --ff-only

Из обновлённой main запустите отчёт по инструкции вашей команды. Если используете названия из задания, команда uv run prime report --date 2026-08-24 даст отчёт с дневными показателями за 23 августа. Сверьте их с расчётами за 23-е в том же часовом поясе.

Итоговый проект проверяется по main на момент отправки. Перед сдачей убедитесь, что нужные PR влиты, и каждый участник отправил ссылку на общий репозиторий через /submit.
